# Pesquisa — canal confiável para sincronizar artigos do Substack

Data: **2026-08-16**

Ticket: [#20 — Research: mapear canal confiável para sincronizar os artigos do Substack](https://github.com/fazedordecodigo/personal_site/issues/20)

Estado: **pesquisa concluída; decisão condicional; nenhum serviço, credencial, workflow ou deploy foi criado ou alterado**

## Decisão

Recomenda-se um **Azure Container Apps Scheduled Job direto**, não um runner do GitHub, executado a cada quatro horas (`17 */4 * * *`, UTC), com uma única réplica, timeout e tentativas limitados. O container confiável busca somente o feed oficial, materializa o candidato, executa os contratos atuais com `npm run verify:snapshot` **antes** de qualquer escrita remota e atualiza somente `content/articles.snapshot.json` por um GitHub App instalado apenas neste repositório. O `push` resultante faz a pipeline normal repetir os mesmos gates e, só então, publicar.

Essa escolha é **condicional**, não uma alegação de funcionamento atual. A documentação da Microsoft confirma que Container Apps tem saída para endpoints públicos e permite cron, retries, timeout, histórico e alertas; ela **não confirma que o Substack aceitará a origem Azure escolhida**. A promoção exige uma prova de rede no ambiente, região, plano, imagem e configuração de egress exatos. Até essa prova existir, o estado é `REDE_AZURE_SUBSTACK_NÃO_EXECUTADA`.

O job é o melhor ajuste porque é uma tarefa curta e conteinerizada: fica desligado entre execuções, reaproveita o código Node existente e evita manter uma máquina/runner privilegiado. [Scheduled Jobs aceitam cron UTC, retry, timeout e paralelismo configuráveis](https://learn.microsoft.com/en-us/azure/container-apps/jobs); execuções são cobradas somente enquanto rodam, sem cobrança de uso quando não há execução, embora registry, logs, Key Vault, rede e NAT possam gerar custos separados ([preços oficiais](https://azure.microsoft.com/en-us/pricing/details/container-apps/)).

O browser continua fora deste fluxo; a própria documentação do Substack confirma apenas a URL pública `https://<publicação>.substack.com/feed`, sem SLA de atualização ou promessa de acesso por nuvens específicas ([Substack Help](https://support.substack.com/hc/en-us/articles/360038239391-Is-there-an-RSS-feed-for-my-publication)).

## Fluxo recomendado

1. O Scheduled Job inicia às `00:17`, `04:17`, `08:17`, `12:17`, `16:17` e `20:17` UTC. Configuração proposta: `parallelism=1`, `replicaCompletionCount=1`, timeout de 30 minutos e uma repetição da réplica. Esses valores e o tamanho de CPU/memória são desenho a medir; a capacidade é oficial ([Container Apps Jobs](https://learn.microsoft.com/en-us/azure/container-apps/jobs)).
2. Uma imagem imutável e fixada por digest contém Node 22.23.2, Java 21, browsers/bibliotecas e o bootstrap auditado. Ela usa somente o default branch confiável, nunca ref de PR, lê o snapshot e seu SHA, busca apenas `https://fazedordecodigo.substack.com/feed`, normaliza e valida três itens. Não expõe endpoint de entrada nem registra XML, token ou conteúdo bruto.
3. Se os três artigos mudaram, o candidato segue imediatamente. Se não mudaram, `fetchedAt` só é renovado quando o snapshot tiver pelo menos 24 horas; assim, o job verifica a cada quatro horas sem criar seis commits/deploys por dia. Quando há candidato, o job executa `npm run verify:snapshot` sobre ele. Qualquer gate — lint, unitário, contrato, HTML, browser, axe ou Lighthouse — impede o commit.
4. Só após todos os gates passarem, a API de conteúdo cria um commit que altera somente o snapshot, com compare-and-swap pelo SHA lido; conflito falha fechado e é reavaliado. O endpoint oficial requer `Contents: write` e o SHA atual do arquivo ([GitHub Contents API](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents)). O commit preserva autor do App, horário, SHA do contrato da imagem e histórico completo; não inclui o feed bruto.
5. Esse `push` em `main` aciona o [workflow normal](../../.github/workflows/site.yml), que repete `verify:snapshot`, publica o artefato e, somente após sucesso e condições de produção, faz deploy. Não se deve usar o `GITHUB_TOKEN` de um workflow para o commit: o GitHub documenta que pushes feitos com ele não geram outro workflow; `workflow_dispatch` e `repository_dispatch` são exceções ([GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token)). Um token de instalação do GitHub App é o ator separado esperado para gerar o `push`; o evento e os controles de path/identidade ainda precisam ser provados em shadow mode.

### Identidade e custódia mínima

- **GitHub:** GitHub App privado, instalado somente em `fazedordecodigo/personal_site`, com `Contents: write`; sem `Actions`, `Workflows`, `Deployments`, `Pull requests` ou `Administration` no runtime. Tokens de instalação podem ser reduzidos a repositórios/permissões concedidos e expiram em uma hora ([autenticação oficial](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation); [permissões para Git](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)). `Contents: write` ainda é amplo dentro do repositório; path exato, compare-and-swap e regras da branch são controles indispensáveis.
- **Azure:** identidade gerenciada atribuída ao job com apenas `Key Vault Secrets User` no segredo da chave privada do App e, se houver ACR privado, apenas pull da imagem. Container Apps pode referenciar Key Vault por managed identity ([segredos](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets)) e usar identidade gerenciada para recursos protegidos pelo Entra ID ([identidade](https://learn.microsoft.com/en-us/azure/container-apps/managed-identity)). A chave do App não entra no repositório, imagem ou GitHub Actions; o token de uma hora é cunhado por execução.
- **Rede:** o ambiente padrão alcança endpoints públicos, mas seus IPs de saída podem mudar. Um workload-profile environment com VNet e NAT fornece IP estático, com custo adicional ([rede](https://learn.microsoft.com/en-us/azure/container-apps/networking); [NAT](https://learn.microsoft.com/en-us/azure/container-apps/custom-virtual-networks#azure-nat-gateway-integration)). IP estático melhora atribuição e controle; **não prova nem garante aceitação pelo Substack**.

## Comparação das opções

| Opção | Compatibilidade e rede | Operação, custo e segurança | Veredicto |
|---|---|---|---|
| **Azure Container Apps Scheduled Job direto** | Imagem customizada reproduz Node, Java e browsers; cron UTC, retry/timeout, escala a zero. Egress público é suportado, mas acesso ao Substack é desconhecido até o probe. | Sem host persistente; paga por execução, mais serviços auxiliares. Managed identity + Key Vault e imagem por digest reduzem credenciais/supply chain. [Azure Monitor oferece alertas por métricas ou logs](https://learn.microsoft.com/en-us/azure/container-apps/alerts). | **Recomendado, condicionado ao prototype.** |
| **GitHub Actions self-hosted runner** | Reutilizaria YAML quase integralmente, mas ainda precisa egress comprovado. Agenda do GitHub pode atrasar/perder jobs e é desabilitada após 60 dias sem atividade em repositório público ([schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)). | O host, SO e ferramentas ficam sob nossa manutenção. GitHub recomenda runner efêmero e alerta que self-hosted em repositório público pode ser comprometido por fork/PR; ARC é a solução oficial de autoscaling em Kubernetes ([referência](https://docs.github.com/en/actions/reference/runners/self-hosted-runners); [restrição para públicos](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access)). Complexidade desproporcional para um cron. | **Não recomendado.** Só fallback em rede já operada, efêmero e isolado de PRs. |
| **Azure Functions Timer** | Node 22 é suportado ([runtime](https://learn.microsoft.com/en-us/azure/azure-functions/functions-reference-node)); timer persiste agenda, não sobrepõe invocação pendente e, por padrão, só tenta de novo na próxima agenda, embora retry de função possa ser configurado ([timer](https://learn.microsoft.com/en-us/azure/azure-functions/functions-bindings-timer); [retries](https://learn.microsoft.com/en-us/azure/azure-functions/functions-bindings-error-pages)). Egress ao Substack continua desconhecido; IP fixo exige desenho de VNet/NAT compatível ([IPs](https://learn.microsoft.com/en-us/azure/azure-functions/ip-addresses)). | Pode ser barato em consumo, mas exige Function App + Storage e um adapter próprio para API/commit; não é ambiente natural para os gates Java/Playwright. A CI ainda faria os gates depois do push. | **Viável, segunda escolha**, se já existir Function App operada e o probe passar. |
| **Azure DevOps Managed DevOps Pool** | Serviço gerenciado com imagem customizável, agentes stateless, acesso de rede controlável e IP estático opcional ([visão geral](https://learn.microsoft.com/en-us/azure/devops/managed-devops-pools/overview?view=azure-devops); [rede](https://learn.microsoft.com/en-us/azure/devops/managed-devops-pools/configure-networking?view=azure-devops)). A integração oficial recomenda GitHub App ([GitHub repositories](https://learn.microsoft.com/en-us/azure/devops/pipelines/repos/github?view=azure-devops)). Egress ao Substack permanece não provado. | Reduz manutenção de VM, mas cria Azure DevOps organization/project, pipeline, pool, service connection e cobrança de VM/NAT para uma única tarefa. | **Tecnicamente forte, não materialmente melhor aqui.** Considerar apenas se a organização já operar Azure Pipelines/Managed Pools. |

## Falhas, alerta e rollback

| Falha | Comportamento obrigatório |
|---|---|
| Feed, timeout, status, XML, contrato ou qualquer gate `verify:snapshot` inválido | Nenhuma chamada de escrita ao GitHub; writer atômico mantém o arquivo anterior; execução falha com código sanitizado e retry limitado. |
| Token, GitHub ou conflito de SHA | Nenhum force-push nem retry cego; reler uma vez ou falhar. O snapshot e produção anteriores permanecem. |
| CI/contrato falha após o commit | O workflow atual não libera artefato/deploy sem sucesso. O snapshot anterior continua recuperável no Git, embora `main` contenha o commit rejeitado pelos gates. |
| Deploy Azure falha ou smoke pós-deploy falha | O repositório não contém hoje rollback automático comprovado. Guardar SHA anterior e redeployar/reverter somente o commit do snapshot é o procedimento proposto, a provar em preview antes de produção; não afirmar atomicidade/rollback Azure sem esse ensaio. |

Criar alerta de log para execução `Failed`, alerta de ausência de sucesso por oito horas e notificação da falha do workflow GitHub. Histórico nativo guarda as 100 execuções mais recentes; logs duráveis vêm do provider configurado ([histórico oficial](https://learn.microsoft.com/en-us/azure/container-apps/jobs#get-job-execution-history)). O SLO de 24 horas é condicionado a: o item aparecer no feed oficial, ao menos uma execução alcançar o feed, GitHub aceitar o commit e os gates e o deploy passarem.

## Estado GitHub observado e tarefa de prototype/provisionamento necessária

Leitura autenticada e sem mutação em **2026-08-16** confirmou: `main` não possui branch protection nem ruleset; `PRODUCTION_DEPLOY_ENABLED=true`; o environment `production` aceita somente a branch `main` e não possui required reviewer; e o nome esperado do segredo do Static Web Apps está cadastrado. O valor e a validade do segredo não são legíveis pela API. No estado atual, não há regra GitHub visível exigindo PR ou revisão antes do push/deploy, mas `Contents: write` e o evento gerado pelo App ainda precisam de shadow proof. Uma futura proteção de branch deve decidir explicitamente se o App escreve direto, recebe bypass restrito ou usa outro fluxo ([GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches); [rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).

Continuam desconhecidos: inventário Azure existente, região/quota, preço efetivo, saúde do token Static Web Apps e conectividade do executor Azure com o Substack.

Abrir uma tarefa futura, com autorização separada, para:

1. reconfirmar em leitura as regras/ambientes/variáveis GitHub no momento da implementação e inventariar recursos/custos Azure;
2. executar um job manual **sem credencial de escrita GitHub** no alvo exato e registrar somente status, content-type, redirects, bytes, código do parser, egress IP e duração em várias execuções; `PROVA_REDE_PASS` exige três artigos válidos, não apenas HTTP 200;
3. implementar/testar serialização canônica, decisão “artigos mudaram ou idade ≥24 h”, compare-and-swap e idempotência;
4. instalar o App/Key Vault e provar em shadow mode que o evento do App inicia `verify:snapshot`, sem deploy; depois provar falha, alerta e rollback em preview;
5. somente então, sob autorização de implantação, habilitar agenda e produção. Se o probe Azure falhar, não migrar às cegas para Functions/Managed Pool; testar o candidato exato. O fallback é um executor efêmero em uma rede já comprovada, ainda usando o mesmo App e snapshot commitado.
